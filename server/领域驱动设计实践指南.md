# Breezy 后端领域驱动设计实践指南

本文面向希望理解 Breezy 后端设计的人，结合 `server/` 中的代码介绍领域驱动设计（Domain-Driven Design，DDD）的核心概念、设计原则及其在真实工程中的取舍。重点不在于给代码贴上“符合/不符合 DDD”的标签，而在于理解：每种边界和抽象解决什么问题，带来什么成本，当前项目为何选择这样的实现。

> 代码路径均相对于仓库根目录。示例反映当前实现；代码会演进，阅读时应以源码为准。

## 1. DDD 是什么：先解决语言和边界，再讨论类与包

DDD 不是一套固定的 Java 包名，也不等于“每个表都建 Entity、Repository、Service”。它是一种复杂业务软件的分析和设计方法，核心是让软件模型持续表达业务人员理解的业务概念与规则。

DDD 通常分成两个互补的视角：

- **战略设计**：确定领域、子域、限界上下文（Bounded Context）及上下文之间的关系，回答“系统中不同模型各自在哪里成立”。
- **战术设计**：在上下文内部使用实体、值对象、聚合、仓储、领域服务、应用服务、领域事件等建模手段，回答“如何表达和执行一条业务规则”。

两者的先后关系很重要：如果边界没有理清，战术模式容易变成样板代码；如果只有包结构没有业务语言，模块也未必真的形成了领域边界。

## 2. 从 `server/` 看模块和可能的领域边界

`server/pom.xml` 将后端组织为多个 Maven 模块：

| 模块 | 当前职责 | DDD 视角的理解 |
| --- | --- | --- |
| `framework/` | 通用分页、异常、Web、缓存、配置等技术能力 | 共享技术内核，不是业务领域模型的容器 |
| `system/` | 用户、角色、资源、权限、通知、任务调度等平台能力 | 一组系统管理上下文；其中用户、权限、调度等仍可继续作为独立子域理解 |
| `business/` | `datasource`、`storage`、`jsonfmt`、`schemaforge`、`reminder` 等业务工具 | 多个业务上下文的代码模块集合，不应仅因共用 Maven 模块就视为一个统一领域 |
| `bootstrap/` | 启动初始化、资源与 schema 同步 | 应用启动和部署引导流程；通常属于技术/运维支撑，而非用户业务子域 |

这些是**代码模块和职责的观察**，不是经过完整领域建模后确认的上下文映射图。Maven 模块、Java package、限界上下文三者不是同义词：一个 Maven 模块可以装多个上下文，一个上下文也可能需要跨多个技术模块。

例如，`com.corwin.reminder`、`com.corwin.datasource` 有各自的 `domain`、`application`、`infrastructure`、`interfaces` 子包，显示出相对清晰的局部模型边界；但它们仍运行在同一个应用和数据库体系中。这是模块化单体的边界，不代表微服务隔离、独立部署或独立数据所有权。

### 2.1 子域与限界上下文

- **子域**是业务问题空间中的划分，例如数据源连接管理、待办与提醒、系统权限管理。
- **限界上下文**是一个模型、术语和规则保持一致的边界。相同词语在不同上下文中可能有不同含义。
- **上下文映射**描述上下文之间如何协作，例如通过应用端口、事件或明确的防腐层转换模型。

不要仅凭文件夹名断言一个完整限界上下文已经建立。验证边界时，可以问：该模块是否拥有自己的术语和规则？谁有权修改它的数据？跨模块调用是否使用稳定、清晰的契约？一个上下文的内部模型是否正在被另一个上下文直接拿来当自己的模型？

## 3. 分层架构：让业务规则不被接口和数据库牵着走

Breezy 常见的业务包结构如下：

```text
reminder/
├─ interfaces/web/       # HTTP、Req/Res、协议转换
├─ application/          # 用例编排、Command、View、事件契约
├─ domain/               # 领域模型、规则、仓储接口
└─ infrastructure/      # JPA/MyBatis、调度、外部技术实现
```

依赖方向的目标是：外层适配内层，业务规则不依赖 HTTP 或数据库访问细节。

| 层 | 应该回答的问题 | 在 Breezy 中的例子 |
| --- | --- | --- |
| `interfaces` | 接收什么协议输入，如何转换和返回？ | `TodoController` 将 Req 转为 Command，再将 View 转为 Res |
| `application` | 这个用例按什么步骤完成？需要协调哪些能力？ | `TodoAppService.create/complete/reorder` |
| `domain` | 什么状态和行为在业务上合法？ | `TodoTask.markDone/shouldFire/update` |
| `infrastructure` | 如何用数据库、框架、队列或外部服务实现端口？ | `TodoTaskRepositoryJpaAdapter`、MyBatis Mapper |

这不是要求每次调用都经过四层，也不是禁止层之间出现 DTO 转换。目标是使业务规则有明确归属，并避免技术细节渗入领域决策。

## 4. 一个完整案例：待办的完成用例

### 4.1 HTTP 接口负责协议转换

`server/business/src/main/java/com/corwin/reminder/interfaces/web/TodoController.java` 中的 `complete` 接收 `TodoCompleteReq`，将它转换成 `TodoCompleteCommand`，调用应用服务，再包装成 `ApiResponse`。

Controller 不决定待办能否完成、不直接读写 Repository，也不处理事务。它是 HTTP 适配器，不是用例本身。

### 4.2 应用服务负责用例协作

`server/business/src/main/java/com/corwin/reminder/application/service/TodoAppService.java` 中的 `complete` 执行的流程大致为：

1. 读取待办；
2. 验证当前状态允许完成；
3. 更新完成附件；
4. 调用 `TodoTask.markDone(...)`；
5. 保存待办与附件；
6. 清理不再引用的文件；
7. 发布提醒变更事件。

这体现了应用服务的职责：协调一个用例涉及的对象和端口，定义事务边界，返回调用方需要的结果。它可以做输入完整性、授权上下文、跨对象协调等工作，但不应把所有业务不变式都堆在里面。

### 4.3 领域实体负责自身行为

`server/business/src/main/java/com/corwin/reminder/domain/model/TodoTask.java` 不只是字段集合。它有 `markDone`、`pause`、`resume`、`shouldFire`、`replaceContentAttachments` 等行为，也封装提醒时间由截止时间提前五分钟计算的规则。

实体以身份连续性为核心：同一个待办在创建、编辑、完成的过程中身份不变，由 `id` 标识。状态和属性可以改变，但调用者不应把“完成待办”表达成随意改写若干数据库字段。

例如：

```java
public void markDone(String completionNote) {
  this.status = TodoTaskStatus.DONE;
  this.completedAt = HighDate.mockInstant();
  this.completionNote = completionNote;
}
```

把操作表达为业务动词有几个好处：行为有统一入口、时间戳与状态变更同步、调用代码可读性较好。它也让将来增加“只有待办状态才能完成”等规则有明确落点。

当前代码中，`TodoAppService.complete` 也有一条“不能重复完成”的校验。这说明规则目前分布在应用服务和实体之间：应用服务在用例入口保护状态转换，实体承担状态修改。若此状态转换是必须对所有调用路径成立的领域不变式，更强的封装方式是在 `TodoTask.markDone` 内校验旧状态，让其他调用者也无法绕过。是否立即移动规则，应基于实际调用路径和规则归属，而不是为了追求“所有校验都在 Entity”机械重构。

## 5. 实体、值对象和领域类型

### 5.1 实体（Entity）

实体具有身份和生命周期。`TodoTask`、`User`、`DatabaseSource` 都有持久化 ID，并通过行为更新状态，因此是实体。

判断实体的关键不是“是否有 `@Entity`”，而是业务是否关心它在变化前后仍是同一个对象。JPA 注解只是当前持久化映射方式。

### 5.2 值对象（Value Object）

值对象由其值定义，不依赖独立身份，通常应不可变，适合表达一个有意义的业务概念。当前代码中 `TodoSaveCommand`、`TodoTaskPageQuery` 等 `record` 是不可变的数据载体，但它们**不因此自动成为领域值对象**：Command 属于用例输入，查询对象属于查询契约。类似 `TodoTaskStatus`、`TodoAttachmentStage` 的枚举也表达了受限取值，但未必承载一个完整的值对象语义。

在 `TodoTask` 中，提醒时间目前是 `Instant`，连接参数目前是多个 `String`、`Integer` 字段。这是直接且实用的映射；代价是类型本身无法表达更强约束。若某个概念拥有稳定的校验和计算规则，可考虑引入 `ReminderTime`、`DatabaseConnectionOptions` 等不可变类型，让非法值更难构造。若它们只是简单字段包装，额外类型只会增加跳转和映射成本。

### 5.3 强类型的收益与成本

使用 `Long`、`String` 作为 ID 易于与 JPA 和现有接口集成，但多个 ID 类型可能被误传。包装为 `TodoId`、`UserId` 可以在编译期阻止部分错误，却增加了 DTO、数据库和日志之间的转换。适合在业务错误代价高、标识混淆常见或边界清晰时引入；不应将“所有 primitive 都包装”当成 DDD 合规门槛。

## 6. 聚合与一致性边界

聚合（Aggregate）是一组需要在一个一致性边界内维护规则的对象；聚合根（Aggregate Root）是外部访问该聚合的唯一入口。聚合的主要意义不是对象图，而是规定：一次业务操作应保证哪些不变式，哪些对象可在该事务中一起修改。

### 6.1 待办与附件的当前边界

`TodoTask` 包含待办自身状态和行为。附件实体 `TodoAttachment` 单独持久化，通过 `todoId` 逻辑关联；`TodoTask` 暂存附件列表并提供替换、排序等操作，应用服务负责批量保存附件。

这可理解为一个务实的聚合协作设计：附件不使用 JPA 级联或物理外键，而通过 ID 关联，符合项目避免物理外键及级联删除的约定。它避免 ORM 对象图、懒加载和级联行为接管数据生命周期，但也意味着数据库不会替应用保证“不能存在孤儿附件”。删除待办时必须由用例显式删除附件，相关写操作必须放在合适的事务中。

DDD 理论会要求认真判断附件是否应作为待办聚合内实体，或作为独立聚合。如果附件的合法性必须与待办同时成立、且生命周期始终受待办控制，聚合根应确保所有写入都经过它；但现实实现受无 FK、无级联约束影响，采用逻辑关联和应用层协调是合理折衷。重要的是不要让其他入口绕过这一协调约定。

### 6.2 聚合不要做得过大

聚合不是“把有关联的表都放进一个对象”。过大的聚合会增加锁竞争、加载成本和并发冲突；过小则可能让必须同时成立的规则无法在一个事务中保护。以业务不变式和一致性要求划边界，而非以数据库外键或 UI 页面划边界。

代码中存在 `TodoTask` 和 `TodoAttachment` 的关联，但是否完全属于一个强一致聚合，需结合附件跨待办复用、修改并发、文件引用计数等业务规则持续判断。当前代码使用多个 Repository 协调这一事实，应在扩展时作为显式设计约束。

## 7. 仓储（Repository）：领域集合的持久化端口

仓储提供领域对象的保存和查询接口，使应用服务不必依赖具体 ORM。`TodoTaskRepository` 位于 `domain.repo`，继承框架的 `DomainRepository<TodoTask, Long>`，并定义待办领域需要的查询；`TodoTaskRepositoryJpaAdapter` 位于 `infrastructure.persistence`，用 JPA 保存单体、用 MyBatis 执行分页查询。

这个例子展示了仓储模式的重点：**领域/应用使用稳定的查询语义，基础设施选择适合的实现**。它也展示了现实取舍：通用 CRUD 抽象放在框架模块可以减少重复，但 `DomainRepository` 返回具体实体并使用 `Long`，并非完全与技术无关的纯理论仓储。接口的价值在于隔离实现细节，而不是消灭所有技术约束。

项目约定分页和动态查询优先在持久化实现层使用 MyBatis Mapper XML / XSQL 处理。复杂列表查询不一定适合将每个筛选组合塞进 Repository 派生方法或领域实体；查询模型可以返回专用 View/Projection，尤其在统计和报表场景中，没有必要强行把只读查询伪装成聚合加载。

常见选择：

- 主键、唯一键、少量固定条件读取：JPA Repository 通常足够。
- 分页、动态筛选、统计、排序白名单：由基础设施层的 Mapper/XSQL 实现，并由 Repository/查询端口提供清晰契约。
- 只读复杂查询：可使用独立查询服务或读模型，不必全部经过聚合仓储。

## 8. 应用服务、领域服务和事务

### 8.1 应用服务编排用例

`TodoAppService` 是应用服务：获取当前用户、读取并保存聚合、协调附件与文件端口、发布应用事件、转换为 View。它使用 Spring `@Transactional` 定义事务，这是应用层通过框架实现用例边界的工程实践。

如果 `TodoAppService` 中出现复杂且可独立表达的业务计算，应考虑将它下沉到实体/值对象或领域服务；如果它在协调多个 Repository、授权上下文和外部端口，则应用服务保留编排通常更清晰。

### 8.2 领域服务不是“更高级的 Service”

领域服务适用于一条真实的领域规则无法自然归属于单个实体/值对象、但仍属于业务模型的情况。它应使用领域语言表达规则，不应成为 Repository 调用、HTTP 请求和 DTO 拼装的杂物箱。应用服务则关注“完成一次用例需要做哪些事”。类名叫 `*Service` 并不能决定其 DDD 角色，应看职责和依赖。

### 8.3 事务边界和外部副作用

数据库事务可以保护一个本地一致性边界，但不能自动回滚已经发送的通知、删除的物理文件或已经注册到内存调度器的任务。若跨数据库与外部副作用直接同步执行，必须考虑失败顺序、重复执行和补偿。

项目的提醒链路使用 `ReminderOutbox`、去重键及调度兜底扫描，说明工程上已处理一部分可靠投递问题。它体现了“本地事务记录意图，再由后续流程发送”的思路；不要据此假定所有通知路径都已实现严格的事务发件箱或 exactly-once。实际保证应按具体实现和调用事务逐条确认，通常更现实的目标是可重试、幂等和可观测。

## 9. 领域事件与模块协作

`TodoAppService` 在待办保存后发布 `TodoTaskReminderChangedEvent`，`ReminderEngine` 通过 `@EventListener` 取消或重新安排内存提醒。这让待办用例不必直接依赖提醒引擎的内部队列实现。

事件是“某件有意义的事情已经发生”的事实陈述，不是所有方法调用的替代品。使用事件可以降低直接耦合、允许多个订阅者独立响应；代价是流程跳转变多、执行顺序和失败传播不再一目了然。

### 9.1 当前事件属于什么

当前 `TodoTaskReminderChangedEvent` 位于 `application.event`，通过 Spring `ApplicationEventPublisher` 发布，并由同一应用内监听器处理。它更准确地说是**应用内事件/模块间通知**。它携带 `todoId`、提醒时间及移除标志，订阅者需要时再查自己的数据，避免把整个 JPA 实体作为事件契约传递。

严格的领域事件通常表达领域中已经发生的事实，例如 `TodoCompleted`；当前事件表达“提醒安排发生变更”，更偏向应用协调信号。这是合理的务实选择，但命名和位置应反映它实际承担的角色。

### 9.2 同步事件不是可靠消息

`@EventListener` 不等于消息队列，也不自动等于“事务提交后执行”。同步监听器可能仍处于发布者调用栈中；若事件在事务提交前改变内存队列，而数据库随后回滚，内存状态和数据库可能不一致。进程崩溃也会丢失仅在内存中的事件。

对可由数据库状态恢复的内存调度，启动时预加载和定时兜底扫描能降低这类风险；若事件必须可靠送达独立进程或外部系统，则需要持久化 outbox、事务提交后投递、重试和幂等处理，而不能只增加一个事件类来宣称可靠。

## 10. 命令、查询和读写模型

`TodoSaveCommand`、`TodoCompleteCommand` 是应用用例的输入；`TodoView`、`TodoDailyStatsView` 是应用层输出；接口 Req/Res 是 HTTP 协议模型。它们分别服务于不同边界，不能因为字段相同就默认共用一个类。

项目同时使用 JPA 与 MyBatis：写入和简单聚合持久化用 JPA，列表和动态查询用 MyBatis。这接近轻量级 CQRS 的“写模型与读模型采用不同实现”，但不代表项目全面采用 CQRS：命令和查询仍在同一应用/数据库中，也没有事件溯源。对后台列表和统计而言，直接优化读取 SQL 往往比把全部数据建成领域对象更简单。

## 11. 数据源领域：业务模型与技术细节的交界

`server/business/src/main/java/com/corwin/datasource/domain/model/DatabaseSource.java` 将数据源生命周期表达为实体行为：`createUser`、`createApp`、`updateUserConfig`、`markTestOk`、`markTestFailed`。它能区分用户数据源和应用数据源，并封装连接测试状态转换。

然而该实体也持有 `jdbcUrl`、驱动类名、主机和认证参数等技术属性。这是有意的领域现实：数据源管理这个业务本身就管理数据库连接配置，技术概念属于它的业务语言，不是所有技术词都必须从领域层剔除。与此同时，JDBC 建连、元数据抽取、密码编解码等 I/O 和实现细节应由应用端口/基础设施承担，而不是放进实体。

当前数据源模型直接使用 JPA 注解并维护扁平字段，方便持久化和编辑表单映射；代价是实体既是领域对象又是 ORM 对象，字段结构容易受到数据库和接口形态影响。可以在规则复杂、字段组合存在强不变式时引入值对象或独立持久化模型；简单 CRUD 场景则可能得不偿失。

## 12. 依赖规则：框架、系统域和业务域

项目明确禁止框架层依赖具体业务域。其意图与依赖倒置原则一致：通用能力定义抽象，业务提供实现，避免框架被某个业务模型绑住。

在 DDD 语境下，还需区别两种依赖：

- **编译依赖**：模块 A 是否 import 模块 B 的类型。
- **业务模型依赖**：A 是否把 B 的内部模型当成自己的语言和规则来源。

允许 `business -> system` 的工程依赖，不代表所有跨域直接依赖都适宜。项目已通过 `FileCommandPort` 之类的接口表达部分跨域调用；新增跨域协作时，优先定义用途明确的端口/契约，只暴露完成用例所需的能力，而不是把另一个模块的 Repository 或 JPA 实体作为公共 API。

## 13. 理论与现实实现的妥协清单

| DDD 理想/原则 | 当前实现与选择 | 收益 | 代价、边界与后续判断 |
| --- | --- | --- | --- |
| 领域层纯粹、不依赖基础设施 | 部分 `domain.model` 使用 JPA 注解、生命周期回调 | 少一层映射，持久化简单，适合模块化单体 | ORM 成为模型约束；复杂持久化变化会影响领域类。高复杂度或多存储需求出现时再评估分离持久化模型 |
| 聚合内对象经聚合根维护一致性 | 待办与附件通过逻辑 ID 关联，应用服务显式协调多个仓储 | 符合无物理 FK、无级联删除约束，生命周期操作可控 | 需要每条写路径遵守同一约定；应用层绕过时可能留下孤儿数据 |
| 仓储表达领域集合 | `DomainRepository` 放在 framework，提供通用 CRUD | 降低重复，模块间接口风格一致 | 通用接口可能超出领域所需，框架抽象不可避免地受 Java/JPA 类型影响；特定领域查询仍应定义在具体 Repository |
| 领域事件在事务提交后可靠传播 | 当前部分用 Spring 应用事件驱动内存调度，配合预加载/扫描恢复 | 实现简单、模块解耦，重启后可按数据库恢复 | 不是持久消息、不保证进程崩溃下不丢；关键外部副作用需要 outbox/重试/幂等 |
| 领域模型只含业务概念 | `DatabaseSource` 直接持有 JDBC 配置 | 连接管理业务可直接表达真实概念 | 需把建连、驱动调用、密钥处理等行为留给端口和基础设施 |
| 写模型与读模型各司其职 | JPA 写入，MyBatis 处理复杂分页/筛选 | 查询可按场景优化，不强迫构造庞大对象图 | 两套映射需要保持一致；查询参数和排序必须由基础设施明确约束 |
| 每个概念都强类型化、值对象化 | 当前大量使用 `Long`、`String`、枚举与 `Instant` | DTO、ORM、SQL 映射简单，开发速度快 | 编译期约束弱；只在规则集中、语义稳定或错误风险高处引入值对象 |
| 每个领域都应建丰富模型 | 一些系统管理能力更偏 CRUD，模型行为相对有限 | 对简单用例保持直白，避免为了模式而模式 | 业务规则增长时要避免服务层持续堆积规则；以规则复杂度为模型投资信号 |

“妥协”不是降低质量的同义词。好的妥协应当是：有具体收益、边界清楚、风险可说明，并且未来有新的业务压力时存在可演进路径。

## 14. 常见误区与检查问题

### 常见误区

1. **“用了四层包结构就是 DDD。”** 包结构只能帮助定位职责，不能证明模型表达了业务规则。
2. **“Entity 必须没有框架注解。”** 这是理想的隔离程度之一，不是衡量业务模型质量的唯一标准。应权衡测试性、复杂度和 ORM 耦合。
3. **“Repository 就是 JPA Repository 的别名。”** Repository 是持久化边界；接口应反映用例需要，具体技术实现留在基础设施。
4. **“所有逻辑都必须放进 Entity。”** 用例编排、跨聚合协调、外部 I/O 不属于单个实体；过度把逻辑塞进 Entity 一样会造成耦合。
5. **“两个表有关联就必须同一个聚合。”** 聚合边界由一致性规则决定，而不是 ER 图决定。
6. **“发了事件就解耦且可靠。”** 事件仍有契约、事务、失败、顺序和幂等问题；进程内事件不是消息中间件。
7. **“所有查询都要先加载聚合。”** 面向列表和统计的查询可以用专门 SQL/read model，避免不必要的对象图和性能成本。
8. **“微服务才需要限界上下文。”** 限界上下文首先是模型和语言的边界；模块化单体也可以清晰地划分它们。

### 评审一条用例时可问

- 这条用例使用了哪些业务术语？这些术语在此上下文中是否定义清楚？
- 哪些规则是必须始终成立的不变式？当前所有入口是否都能保证它？
- 哪个对象拥有该行为？行为放在此处是否减少了非法状态和重复规则？
- 用例涉及哪些聚合？需要强一致的范围是否过大或过小？
- 应用服务是否只做编排，还是已经承担了大部分领域决策？
- Repository 契约表达的是业务意图，还是泄漏了 Mapper/JPA 技术细节？
- 外部调用、文件删除、事件发布与数据库事务失败时，系统会留下什么状态？如何重试或恢复？
- 跨上下文是否传递内部实体？对方是否被迫理解本上下文的模型？
- 新增抽象解决了实际变化点，还是只是为了满足某种理论形式？

## 15. 在 Breezy 中实践 DDD 的建议

1. **先写清业务词汇和规则。** 通过需求和代码找到名词、状态、行为及边界，再选择类和包。
2. **优先保护不变式。** 对关键状态转换提供清晰的行为入口，并确认应用内没有绕过入口的写路径。
3. **以一致性划聚合。** 只把必须原子保证的对象放在一个强一致边界，不按表关系或页面范围扩大聚合。
4. **应用服务编排，领域模型决策。** 外部 I/O 通过端口完成，业务规则留在合适的领域对象或领域服务。
5. **查询按查询需求设计。** 遵循项目的分页/动态查询约定，用 MyBatis/XSQL 实现复杂读取，不为了“纯 DDD”制造低效对象加载。
6. **跨域依赖使用稳定契约。** 避免公开 JPA 实体和内部 Repository；共享事件只表达必要字段和稳定语义。
7. **明确可靠性级别。** 进程内通知、启动恢复、outbox、外部消息投递是不同级别的机制，不混为一谈。
8. **按复杂度投资模型。** 简单 CRUD 保持直白；当规则重复、状态转换复杂、并发或外部副作用风险上升时，再增加值对象、聚合边界、幂等机制等设计。
